## Recommended inference architecture

Keep the fast, one-stage LightGBM/ONNX family as the production backbone. It has the strongest real leaderboard evidence and fits the single-core, small-package runtime. Structure the feature set around physiology rather than protocol position:

1. **Local sensor branch (primary):** per-window BVP pulse/noise, HR/IBI variability, EDA tonic/phasic activity, and temperature level/trend. Prefer features available from the current 10-second window plus short past-only summaries. This branch should remain useful when a recording is trimmed, reordered, or mixed with another protocol.
2. **Bounded context branch (optional):** causal rolling baselines and changes over the previous 30–180 seconds, with explicit missingness/quality indicators. It may help distinguish elevated exertion from acute stress, but must not use whole-recording statistics, future windows, input duration, or start position.
3. **Calibrated fusion:** if combining TULUI and a new model, blend their class probabilities using out-of-fold predictions from held-out people. Select class bias and any causal smoothing only inside those folds. Do not tune them against the leaderboard repeatedly.

Use LightGBM for the first iteration, not a sequence network: current evidence says the dominant risk is distribution shift and evaluation mismatch, while a sequence model would add runtime and give a small subject set more ways to overfit. Keep the three-class macro-F1 objective visible, with per-class Stress F1 tracked separately because it is the weakest class and is equally weighted.

## Validation protocol before an upload

1. **Reproduce the official contract:** run the packaged model through the official `ADM_Base` call; output one valid label per input row with the original index. Benchmark mean runtime over 50 calls on the evaluation-like full recording, single core. Official quality uses the mode label per 10-second window and macro-F1 over Stress, Activity, Rest.
2. **Use subject-held-out folds, not random windows.** Generate out-of-fold predictions for every training person. Keep every recording from a person in one fold. Aggregate F1 from pooled windows using the official class order and zero-division behavior.
3. **Score several input constructions:** untouched full recordings; random trims; phase-reordered recordings; phase-reordered recordings with varied retained lengths; and same-person cross-session mixtures. Report each score and each class F1. Treat generated splices as stress tests, not estimates of the hidden score.
4. **Audit information availability:** compare predictions on a fixed prefix when the suffix is changed. For a jury-ready model, prefix predictions should not change because later samples changed. Any global normalization, centered window, future lag, or whole-recording summary fails this check and should be removed or replaced with a past-only computation.
5. **Release gate:** require a repeatable gain across multiple held-out-person folds, no material regression on the phase-reordered and mixed-session stress tests, zero fallback/errors on real recordings, and confirmed inference time/package limits. Submit only after the gain survives the same folds with a second seed.

## Evaluation mismatch: what is known and what is not

The local harness matches the public scoring formula and output contract. It cannot match hidden labels, exact hidden participants, or Agorize's runtime hardware. Submission history demonstrates this: local training-order quality badly misranks submissions; T4 mixed-session ranking correlated better, but still had about four points of fit error and overestimated V5.1 by around ten. Thus:

- Trust the official leaderboard as the only ground truth for hidden-test score.
- Use person-held-out, pooled-window CV to compare model changes; use shuffled tests to test robustness, not to forecast an exact leaderboard score.
- Record quality and speed separately whenever the platform exposes them. A total score alone cannot tell whether an apparent gain came from a better classifier or a faster runtime.
- Prefer a small set of controlled submissions that answer one question each (e.g. TULUI-fast speed effect, then a quality change). Preserve the best-scoring artifact.

## Practical next sequence

1. `TULUI_fast.zip` has already been uploaded and the public leaderboard confirms **74**. Faster inference alone did not add a leaderboard point.
2. Upload `submissions/candidates/TULUI_shuffle_aug.zip` as the next quality probe. It adds the shuffle recipe to the 145-feature TULUI model; five seeds show a repeatable local gain, while the official score remains unknown.
3. Compare each platform score against the existing 74 and record quality/speed separately if the platform exposes both. The local T3+speed total is diagnostic only.
4. Continue with a no-look-ahead TULUI-derived model for jury readiness. Keep V5.1 as a robustness comparator, not the default backbone.

The 77 target is plausible but not yet supported by current evidence. The speed-only submission stayed at 74; a quality change must now carry the next attempt, and only an actual platform result can establish progress toward 77.
